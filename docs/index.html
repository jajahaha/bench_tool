01

快速开始

PG
PostgreSQL
初始化并运行基准测试，使用 psql 客户端
bash
# 初始化 ./db_shell_bench.sh init -s 1 -h localhost -p 5432 -U postgres # 基准测试 ./db_shell_bench.sh -h localhost -p 5432 -U postgres -c 4 -n 100 benchmark
OG
OpenGauss / GaussDB
自动检测 gsql 客户端，回退 psql；密码 URL 编码处理特殊字符
bash
# OpenGauss 初始化 ./db_shell_bench.sh -t opengauss init -s 1 -W 'Pass@123' # GaussDB 时间模式 ./db_shell_bench.sh -t gaussdb -W 'Pass@123' -c 4 -T 60 benchmark
HV
Heavy 模式
更复杂的混合读写测试，10 条 SQL/事务，包含范围扫描和聚合
bash
./db_shell_bench.sh -M heavy -c 4 -T 60 benchmark # 5读 + 3写 + 2历史查询 # 范围扫描 · 聚合 · 时间倒序

架构设计

├── 参数解析层 ← 提取命令词(init/benchmark)，解析 -h/-p/-U/-W/-M 等
├── 连接层 ← detect_client() → gsql/psql · get_conn_str() → URL编码 · db_exec() · db_exec_quiet()
├── 初始化层 ← init_database() → 建表 · 分批插入 · 建索引 · VACUUM ANALYZE
└── 基准测试层 ← build_txn_sql() · run_benchmark_single() · run_benchmark_multi() · run_benchmark_time() · print_progress()

数据模型

表名主键数据量 (scale=N)说明
{prefix}_branchesbidN分行表
{prefix}_tellerstidN × 10柜员表
{prefix}_accountsaidN × 100,000账户表（主表）
{prefix}_history无动态增长历史记录表
初始化进度

accounts 表按 100,000 行/批次分批插入，每批次显示已完成行数、耗时、预估剩余时间、速率。建索引、VACUUM ANALYZE 各阶段独立计时。

客户端自动选择

opengauss/gaussdb 类型自动检测客户端：有 gsql 时使用 gsql，否则回退 psql（兼容 PostgreSQL 协议）。密码通过 URL 编码的连接字符串传递，特殊字符（@、:、/等）自动处理。

03

测试模式

tpcb — 轻量模式

5 条 SQL / 事务，经典 TPC-B 模型

3 × UPDATE（账户、柜员、分行余额）

1 × SELECT（查询账户余额）

1 × INSERT（插入历史记录）

写密集 · 点查询 · 单行操作

BEGIN; UPDATE accounts SET abalance += delta WHERE aid = ?; SELECT abalance FROM accounts WHERE aid = ?; UPDATE tellers SET tbalance += delta WHERE tid = ?; UPDATE branches SET bbalance += delta WHERE bid = ?; INSERT INTO history VALUES (...); COMMIT;
heavy — 重量模式

10 条 SQL / 事务，混合读写负载

5 × 读操作（点查询 + 范围扫描 + 聚合）

3 × 写操作（UPDATE 余额 + INSERT 历史记录）

2 × 历史查询（按时间倒序）

混合读写 · 范围扫描 · 聚合查询

BEGIN; SELECT ... WHERE aid = ?; -- 点查询 SELECT ... WHERE bid = ?; -- 点查询 SELECT ... WHERE tid = ?; -- 点查询 SELECT ... ORDER BY aid LIMIT 10; -- 范围扫描 SELECT avg(...) WHERE bid = ?; -- 聚合查询 UPDATE accounts SET ...; -- 写 UPDATE tellers SET ...; -- 写 UPDATE branches SET ...; -- 写 INSERT INTO history ...; -- 写 SELECT ... ORDER BY mtime DESC; -- 历史查询 COMMIT;

05

Undo 回收测试

OpenGauss UStore MVCC 快照损坏复现
发现比 "snapshot is stale" 更严重的问题 — 静默返回错误数据而不报错
正确行为 · GaussDB / Oracle

undo 记录被回收后 → 游标报 "snapshot is stale"

用户知道数据不可用，可以重试

ERRCODE_SNAPSHOT_STALE

BUG · OpenGauss 6.0

undo 记录被回收后 → 不报错，静默返回当前数据

普通 SELECT 返回 val≠0 而非快照值 val=0

用户以为数据正确，其实已经错了 — 比 "snapshot is stale" 更严重

触发原理

两层 undo 回收机制

正常回收：尊重 oldest_xmin，只回收已提交且无人引用的 undo 记录
强制回收：undo_used 超过 undo_threshold（80% × undo_space_limit）时，绕过 oldest_xmin 强制回收

1
创建 ustore 表，插入 val=0 数据
↓
2
Session 1 开启长事务游标，FETCH 获取快照数据
↓
3
N 个并发 BEGIN + UPDATE 全表 + pg_sleep + COMMIT，积累 undo_used 超过阈值
↓
4
强制回收触发，绕过 oldest_xmin，回收游标快照需要的 undo 记录
↓
5
游标继续 FETCH → undo 链截断 → 报 "snapshot is stale"（GaussDB）或静默返回当前值（OpenGauss bug）

自动配置

脚本自动配置以下参数

undo_space_limit_size = 102400（800MB，阈值 640MB）
undo_snapshot_stale_check = on（确保报错功能开启）

undo test examples
# GaussDB — 应触发 "snapshot is stale" 报错 ./undo/test_snapshot_too_old.sh -t gaussdb -h localhost -p 8000 -U root -W 'Pass@123' # OpenGauss — 检测静默 MVCC 损坏或 "snapshot is stale" ./undo/test_snapshot_too_old.sh -t opengauss -h localhost -p 5433 -U gaussdb -W 'Enmotech@123' # 加大 undo 压力 ./undo/test_snapshot_too_old.sh -t gaussdb -r 50000 -R 200 -C 16 -P 30 -S 10 -W 'Pass@123'
注意事项

仅适用于 OpenGauss/GaussDB（PostgreSQL 无 undo 机制）
需要 enable_ustore=on
检测的是 MVCC 快照静默损坏，不仅限于 "snapshot is stale" 报错
错误信息搜索包含 "snapshot is stale" 和 "snapshot too old" 两种
